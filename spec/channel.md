# The conda channel

The hosted registry serves every published package as a conda channel, so
that `pixi` and any other conda client can install packages with no mopm
tool, and so that `mopm` can read the same files. This page is what a client
can rely on. Each part is marked: **v1** is part of the contract, **planned**
is not yet promised.

## Hosts

Each stage has a site `<site>` (prod `mopm.dev`, gamma `gamma.mopm.dev`, beta
`beta.mopm.dev`). The API and the sparse index are at `https://api.<site>`
and the channel is at `https://conda.<site>/`; the site itself
(`https://<site>`) is the website and is not the API.

| stage | `<site>` | API and index | channel |
|---|---|---|---|
| prod | `mopm.dev` | `https://api.mopm.dev` | `https://conda.mopm.dev/` |
| gamma | `gamma.mopm.dev` | `https://api.gamma.mopm.dev` | `https://conda.gamma.mopm.dev/` |
| beta | `beta.mopm.dev` | `https://api.beta.mopm.dev` | `https://conda.beta.mopm.dev/` |

The channel host is separate from the API host: it serves static files only,
sets no cookies and has no API. Beta and gamma are disposable: their data can
be wiped, so nothing should be locked to them except for testing.

## Layout (v1)

```text
https://conda.<site>/
  noarch/
  linux-64/
  linux-aarch64/
  osx-arm64/
    repodata.json                 all resolvable packages of the subdir
    repodata.json.zst             the same bytes, zstd-compressed
    current_repodata.json         only the newest version of each name
    mojo-<name>-<version>-<build>.conda
    repodata_shards.msgpack.zst   planned, see Sharded repodata
    shards/<sha256>.msgpack.zst   planned
```

- The four subdirs always exist. A subdir with no packages has a valid,
  empty `repodata.json` (`"packages": {}` and `"packages.conda": {}`).
- `repodata.json` follows the conda repodata layout: `info.subdir`,
  `packages` (always empty: only `.conda` archives are published),
  `packages.conda`, and `removed`.
- Every entry in `packages.conda` is generated by the registry from the
  validated package manifest. It is never copied from the uploaded archive.
  Entries carry `name`, `version`, `build`, `build_number` (always 0),
  `depends`, `sha256`, `size` and `subdir`. They never carry `features`,
  `track_features` or `constrains`. `depends` only names other `mojo-*`
  packages, the exact compiler requirement, and native libraries: any
  conda package, as a well-formed requirement (`name`, `name version` or
  `name version build`, the name in lower-case letters, digits, `.`, `_`
  and `-`). The registry warns, and does not refuse, when conda-forge does
  not list a name (`warnings` of the publish status).
- Dependency spelling in `depends`: the compiler is `mojo-compiler ==<exact>`
  (for example `mojo-compiler ==1.0.0`, the version in the build string); a
  native library uses its conda package name (the library `openssl`
  becomes the dependency `openssl`); another Mojo package is
  `mojo-<name>` with its version constraint.
- `removed` lists the file names (`mojo-<name>-<version>-<build>.conda`) of
  both yanked and tombstoned (taken-down) versions of that subdir. A client
  holding a lock that names a listed file learns from the list that the
  version is no longer offered. The list is the same for either state; the
  sparse index says which one it is.
- The writer is deterministic: keys sorted, no timestamps, so the same set of
  versions always produces the same bytes.
- `current_repodata.json` holds, per name, the newest published (not
  yanked) version with all its builds. It is for fast solves; a client
  that needs an older version reads `repodata.json`.

## Package naming (v1)

- The file is `mojo-<name>-<version>-<build>.conda`. The conda package name is
  `mojo-<name>` where `<name>` is the mopm name (the import name). `pixi add
  mojo-json` installs the package whose import name is `json`.
- The build string is `mojo<compiler>_<n>` for the exact compiler the `.mojoc`
  was built with, for example `mojo1.0.0_0`. `n` is always 0. A version's file
  set is fixed when it is committed, so supporting a new compiler means
  publishing a new version.
- The version is `MAJOR.MINOR.PATCH` (grammar in `api/openapi.yaml`,
  `Version`): three numbers, no leading zeros, no pre-release or other
  suffix. A package whose `info/index.json` names any other spelling of the
  version is rejected. Versions order numerically by major, then minor, then
  patch, which is conda ordering for this grammar.

## Inside a package (v1)

A client reads these paths under the conda prefix:

```text
lib/mojo/<name>.mojoc          the compiled Mojo package
lib/mojo/<name>.mopm.json      the embedded metadata (package-metadata.schema.json)
lib/<soname>                   native libraries the package declares, if any
lib/mojo/<name>.bins/<bin>.mojo  the source of a program the package ships (`[targets] bins`), if any
```

A program is a file of Mojo source, `<bin>` being lower case letters, digits and
underscores. It is data: nothing runs it at install time, and mopm builds it on
the machine that runs it (`mopm run --bin <name>:<bin>`). The registry accepts no
other file below `lib/mojo/<name>.bins/`.

`<name>.mopm.json` is the source of truth for dependencies and native
libraries; its `schema` field is 1 and a higher value is refused. Paths inside
it are relative to the file. The registry refuses archives that contain
anything outside the paths it allows (no `bin/`, no link or activate
scripts, no symlinks or hardlinks, no executable code outside declared native
libraries). A client that extracts a package applies the same rules and treats
a violation as a corrupt package.

## Immutability and yank, as a client sees them (v1)

- **Published files never change.** The bytes at `<subdir>/<filename>` are the
  same forever; `.conda` files are served with a long cache lifetime. The
  sha256 in `repodata.json`, in the sparse index (`index.md`) and in a lock
  must be the same; a difference is an error that names all the values.
- **Yank** hides a version from new resolution. The entry leaves
  `packages.conda` and `current_repodata.json` and is listed under `removed`
  in `repodata.json`; the file itself stays downloadable at its exact URL, so
  an existing lock keeps installing it. The sparse index line changes to
  `state: yanked` with the reason. `mopm` prints a warning for a locked
  yanked version; plain conda clients simply no longer pick it.
- **Takedown** (administrators only, for malware, legal or abuse reasons)
  removes the bytes. The URL then answers 410; a client treats 403 and 404
  from the channel host as "unavailable" too. The sparse index line changes to
  `state: tombstoned` with a reason code, and the version is added to
  `/index/takedowns.json`. Its file is also listed under `removed` in
  `repodata.json`, like a yanked one. `mopm` shows the reason for a locked version; a
  plain conda client only sees the error.
- **State changes are one way where it matters.** A version is `published`
  or `yanked` and can move between the two; a pending version cannot be
  yanked; a tombstoned version never changes. The registry refuses any other
  change with `invalid_transition` (HTTP 409).
- **A number is never reused.** A rejected or taken-down version cannot be
  published again with different bytes.
- Repodata and index files are the only mutable objects. They have a short
  cache lifetime (about a minute) and are rewritten last, after the package
  files they mention exist.

## Sharded repodata (planned)

To keep solves fast as the channel grows, the registry plans to also write
sharded repodata (conda enhancement proposal 16): one small index of shard
hashes per subdir, and one immutable, content-addressed shard per package
name. Clients must not depend on it in v1: `repodata.json(.zst)` and
`current_repodata.json` stay available either way. Whether the pinned `pixi`
reads shards from a plain static channel is not yet established.

## Not in the channel

No signatures in v1: integrity rests on TLS, create-once storage and the
sha256 pinned in a lock. A signed snapshot is a later design and would not
change the layout above.
